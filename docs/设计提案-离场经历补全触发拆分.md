# 设计提案：把「离场经历补全」的触发判据从「角色位置变化」改为「本轮新出现在现场」

> 基线：main @ dcac262（2026-10-03）
> 范围：地图群「入场包」触发逻辑（现场所见 / 事件补全）
> 状态：已实现并验证（2026-10-03 按本方案落地；selfcheck:scene 第 9 段为回归钉，旧代码下变红）

## 0. 一句话

群聊有两个入场包功能——**现场所见**（进门第一眼看到什么）和**事件补全 / 离场经历**（离场期间他经历了什么）。两者目前共用同一个触发判据：**角色自己的位置发生变化**。这导致「用户主动移动场景到某角色处」时，该角色两个都不触发。建议把两者的触发集合拆开：现场所见维持「位置变化」，离场经历改为「本轮新出现在现场」。

## 1. 系统现状（基于当前 main）

### 1.1 术语

- **现场（present）**：地图群里 = 位置等于当前场景的全部角色，是**代码事实**（由 locations 表派生），不是模型判断。
- **入场包**：现场所见（source=现场所见）+ 离场经历（source=离场经历），由 GroupSession.beginEntryKit() 并行执行。

### 1.2 触发点

GroupSession.maybeSnapshotEntrants(before, note)（src/group/engine.ts:542）：

```ts
const entrants = after.present.filter(n =>
  this.byName.has(n)
  && (after.scene === undefined
    ? !before.present.includes(n)        // 平面群：present 差集
    : afterLoc[n] !== beforeLoc[n]))     // 地图群：位置变化
```

调用点两处：
- speak() 步骤 7（engine.ts:849，note='新进现场'）；
- correct() 纠正窗口落位后（engine.ts:1276，note='纠正窗口进场'）。

beginEntryKit(entrants)（engine.ts:529）把**同一个集合**同时喂给两个子任务：

```ts
await Promise.all([this.runSceneSnapshot(targets), this.runOffStory(targets)])
```

- runSceneSnapshot(targets)（engine.ts:425）：调 askSceneSummarizer 生成一份白描，注入每个 target（source=现场所见，无 mid）。
- runOffStory(targets)（engine.ts:460）：对每个 target 用 store.absenceStartId(name)（src/store.ts:264）取「最后一次离场时的消息 id」，取该 id 之后的消息作为离场窗口；窗口为空或 absenceStartId === undefined（首次进场）则跳过；随后 askOffStoryDiscovery（1 次）+ askOffStoryPOV（每事件×参与者 1 次）注入 source=离场经历。

speakAs 在接力选中某人发言前，会等 this.sceneSnapshot.targets 完成（engine.ts:979-983）。

### 1.3 用户移动场景时的实际行为

speak() 阶段一（engine.ts:717-736）：用户从 A 移到 B 时，**只更新此前与用户同处 A 的同行者**的位置（随行/留守/转往），B 的原住民位置不动；随后 present 重算 = B 的全部在场者。

于是 maybeSnapshotEntrants(before, ...)：
- B 的原住民：beforeLoc = B，afterLoc = B → 位置未变 → **不是 entrant**；
- 从 A 随行到 B 的人：beforeLoc = A，afterLoc = B → 是 entrant。

**结论：用户走到某角色所在场景时，该角色不触发入场包（现场所见与离场经历都没有）。** 这是当前规范明写的设计：SPEC §4「characters colocated in the destination scene … are not entry-kit targets (nothing is new to them)」、§5.8「only characters whose location changed」、§1.1 步骤 7。

现有回归钉：scripts/selfcheck-scene-offline.ts:177-180（用户 ⊘ 手选到场景二，一直在场景二的丙**不得**获得现场所见；随行的甲必须获得）。

### 1.4 语义拆解

| 事件 | 现场所见（现在） | 离场经历（现在） |
|---|---|---|
| 角色位置变化进入当前场景（随行 / 被叫进来） | ✓ | ✓（若有离场窗口） |
| **用户移动场景，目的地原住民** | ✗ | **✗ ← 本提案针对** |
| 纠正窗口把角色放进当前场景 | ✓ | ✓（若有） |
| 平面群：present 差集 | ✓ | ✓（若有） |

## 2. 问题陈述

- **现场所见**应当只给「真正进门的人」：原住民本来就在屋里，没有「第一眼」，跳过是正确的。
- **离场经历**的语义是「补全角色不在场期间做了什么」。当用户在 A、角色在 B 时，该角色相对用户主线**就是不在场**——这段时间他身上发生的事在消息流里没有任何出处。absenceStartId 也能正确定位出他的离场窗口。但触发被「位置变化」这同一判据卡掉，导致**永久性记忆空白**。
- 结果是**不对称**：角色走到用户处会补，用户走到角色处不补。例：用户在 A、角色也在 A → 用户离开去 C（角色留守 A，离场窗口自此开始）→ 用户回到 A（角色位置未变）→ 不触发，角色永远想不起用户不在时自己做了什么。
- 该行为**不是代码错误，是判据设计问题**：两个语义不同的功能共用了同一个集合。

## 3. 拟议方案

### 3.1 核心

拆分触发集合：

- **现场所见**：沿用现行判据（地图群 = 位置变化；平面群 = present 差集）。
- **离场经历**：改为 after.present − before.present（本轮新出现在现场者），不区分「是他走过来」还是「你走过去」。
- speakAs 的等待集 = 二者并集（新到场者发言前必须等自己的记忆落盘）。

### 3.2 精确改动点

maybeSnapshotEntrants（保持签名，测试直接调用它）：

```ts
maybeSnapshotEntrants(before: SceneAccess, note = '新进现场'): void {
  const after = this.sceneAccess()
  const beforeLoc = before.locations ?? {}
  const afterLoc = after.locations ?? {}
  const presentNow = after.present.filter(n => this.byName.has(n))
  // ① 现场所见：真正进门的人（判据不变）
  const sceneEntrants = presentNow.filter(n =>
    after.scene === undefined ? !before.present.includes(n) : afterLoc[n] !== beforeLoc[n])
  // ② 离场经历：本轮新出现在现场的所有人（含你走过去时一直在那儿的原住民）
  const newlyPresent = presentNow.filter(n => !before.present.includes(n))
  if (sceneEntrants.length === 0 && newlyPresent.length === 0) return
  const job = this.beginEntryKit(sceneEntrants, newlyPresent)
  this.sceneSnapshot = job
  this.enqueueBg(() => job.done.then(() => undefined))
  this.judgeLog({ phase: '现场所见', note: note + '：现场所见 ' + (sceneEntrants.join('、') || '（无）') + '；离场经历 ' + (newlyPresent.join('、') || '（无）') })
}
```

beginEntryKit：

```ts
private beginEntryKit(sceneEntrants: string[], offStoryTargets: string[]): { targets: Set<string>; done: Promise<void> } {
  const targets = new Set([...sceneEntrants, ...offStoryTargets])   // speakAs 等待集 = 并集
  const done = (async () => {
    await Promise.all([
      sceneEntrants.length > 0 ? this.runSceneSnapshot(new Set(sceneEntrants)) : Promise.resolve(undefined),
      this.runOffStory(new Set(offStoryTargets)),                    // 内部仍按 absenceStartId 过滤首次进场
    ])
  })()
  return { targets, done }
}
```

runSceneSnapshot / runOffStory 主体不变。runOffStory 已自带两道闸：absenceStartId === undefined 跳过（首次进场）、窗口为空跳过。

### 3.3 为什么 runOffStory 用 newlyPresent 而不是并集

随行且此前一直在场的人（A→B 跟随）在 before.present 与 after.present 中都存在 → 不属于 newlyPresent，不给离场经历。这是正确的：他与用户全程未分开，没有新的离场窗口。附带修正一个现存隐患——现行代码会把「历史上曾有离场窗口、但本轮只是随行」的人再喂进 discovery（靠提示词里的「不得与已有离场经历重复」缓解），改为 newlyPresent 后自然消除。

## 4. 行为矩阵（改后）

| 场景 | 现场所见 | 离场经历 | 说明 |
|---|---|---|---|
| 角色位置变化进入当前场景（随行/被叫进来），此前不在场 | ✓ | ✓ | 与现状一致（回归者） |
| 随行且此前一直在场（未分开） | ✓ | ✗ | 进门需要白描；无新分离 |
| **用户移动场景，目的地原住民** | ✗ | **✓** | 本提案新增（有窗口时） |
| 目的地原住民，此前从未在用户场景出现过 | ✗ | ✗ | absenceStartId === undefined（首次，不虚构前史） |
| 纠正窗口把角色放进当前场景 | ✓ | ✓ | 与现状一致 |
| 平面群（无地图） | ✓ | ✓ | newlyPresent === sceneEntrants，行为完全不变 |

## 5. 不变量

1. present 仍是位置表派生的代码事实，方案不改场景/位置判定。
2. absenceStartId 仍是唯一窗口来源；无窗口不补（不虚构前史）。
3. 每条注入仍先写 ledger 行再落文件（INV 2），source=离场经历，无 mid，当前轮。
4. speakAs 的等待集等于「所有将被注入记忆的人」，保证「先有记忆再开口」。
5. 判断触发仍是纯代码（不花 Jev）；仅补全本身是 LLM 调用（发现 1 次 + 每事件×参与者 1 次渲染）。

## 6. 测试与文档

- **新增回归钉**（建议放 selfcheck-router 或 selfcheck-scene）：角色曾在用户场景出现 → 用户离开 → 用户回到该角色所在场景 → 断言该角色记忆新增 source=离场经历，且**没有** source=现场所见。
- **既有钉子**：selfcheck-scene 第 2 段「丙一直在目的地且此前从未在场」仍成立（该角色 absenceStartId 为 undefined，改后依旧不补），只需补一条「也无离场经历」的断言以锁定边界。
- **SPEC 同步**：§1.1 步骤 7、§4、§5.8、§5.9（现文均写「only characters whose location changed / same pure-code diff」，需改为两个集合）。

## 7. 备选方案与取舍

| 方案 | 内容 | 取舍 |
|---|---|---|
| **A（本提案）** | 拆分两个触发集合 | 语义最准；改动集中在 maybeSnapshotEntrants / beginEntryKit；新增 LLM 调用 |
| B | 维持现状，仅在文档写明「用户走过去不补」 | 零风险、零成本；保留记忆空白与不对称 |
| C | 两半都改成 present 差集 | 驳回：原住民每次被到达都会拿到一份「进门第一眼」白描，语义错误且无谓开销 |
| D | present 差集 + 更细的窗口裁剪 | 过度设计；absenceStartId 已给出正确窗口 |

## 8. 影响、成本与风险

- **新增成本**：以前「用户走到有旧识的场景」零 LLM 调用；改后可能多 1 次 askOffStoryDiscovery + N 次 askOffStoryPOV（N = 命中事件 × 参与者，上限 4×4）。受「必须有离场窗口且窗口非空」闸门约束，首次见面的场景不触发。
- **延迟**：新到场者若被接力选中发言，需等补全落盘（现机制已如此，只是集合变大）。
- **行为可逆**：纯增量注入，失败即不注入（维持现状），可用记忆面板/纠正窗口撤回。
- 不改变路由、知情、状态账本、rebuild 语义。

## 9. 待交叉验证的问题

1. **语义**：相对用户主线「分开」是否等价于「离场」、从而应补离场经历？（本提案认为等价；若认为「离场」严格指角色自己离开现场，则应维持现状。）
2. **成本接受度**：走到有旧识的场景可能触发一次发现调用，是否可接受？是否需要加「离场时长/消息数下限」以减少小动作触发？
3. **窗口取法**：原住民的离场窗口 = 他上次离开现场之后的消息（通常是用户在别处的剧情，他本人看不见）。用这段作为「他离场期间发生了什么」的依据是否合理？（提示词本就从这段里提取「对他的指令/约定/他人提到他的打算」再合理延伸。）
4. **等待集**：sceneSnapshot.targets 取并集是否会明显加长接力发言的等待？是否需要超时上限？
5. **开关**：是否需要一个群级开关（如 statusRecord 那样）让用户自行关闭「到达即补全」？
